## 1. Αποφάσεις

### 1.1 Τρόπος δουλειάς

- **Σχεδιασμός, αποφάσεις και μικρά builds γίνονται στο chat του Project** («Ομοσπονδία Backgammon»). Εκεί διαβάζεται κάθε φορά ο τρέχων κώδικας του `main` κατευθείαν από το δημόσιο GitHub repository, χωρίς ανέβασμα αρχείων.
- Από το chat παραδίδονται **μόνο τα αρχεία που άλλαξαν**. Ο Γιάννης τα ανεβάζει σε branch από το GitHub (Add file → Upload files), ελέγχει στο Vercel preview και κάνει merge.
- **Στο Claude Code πηγαίνουν όσα κερδίζουν καθαρά από αυτό:** μηχανικές αλλαγές σε πολλά αρχεία, `npm install`, δοκιμές με Firebase Emulator / Playwright. Σε κάθε βήμα ο σχεδιασμός στο chat λέει ρητά πού προτείνεται να γίνει η υλοποίηση.
- Το repository πρέπει να μένει **χωρίς μυστικά** (κωδικούς, κλειδιά API), αφού είναι δημόσιο. Το Firebase web config δεν είναι μυστικό.
- Ο Γιάννης κάνει πάντα ο ίδιος το merge.

### 1.2 Changelog εφαρμογής

- Μεταφέρεται από το `App.jsx` σε **ξεχωριστό αρχείο** `src/config/changelog.js`.
- **Τρέχουσα ημέρα:** καταχωρήσεις ανά build, όπως σήμερα.
- **Προηγούμενες ημέρες:** **μία ημερήσια σύνοψη** (2–7 γραμμές, για τον χρήστη). Στο πρώτο build κάθε νέας ημέρας, όποιος το κάνει (chat ή Claude Code) συμπτύσσει τις καταχωρήσεις της προηγούμενης σε σύνοψη.
- Κάθε γραμμή έχει **κοινό**: `"all"` (όλοι) ή `"admin"` (μόνο διαχειριστές). Ο επισκέπτης βλέπει μόνο τις `"all"`, και η ένδειξη «νέο» (κόκκινη κουκκίδα) εμφανίζεται μόνο όταν υπάρχει νέα γραμμή ορατή στον συγκεκριμένο χρήστη.
- Η αναλυτική τεχνική ιστορία μένει στο Git (commits, PR) και στο `CLAUDE.md`. Το changelog της εφαρμογής είναι μόνο «τι κερδίζει ο χρήστης».

### 1.3 Διάσπαση κώδικα

- **Φάση 1 (build R2):** μηχανική μεταφορά σε ενότητες όλων όσων βρίσκονται **έξω** από το component `TournamentManager`, **χωρίς καμία αλλαγή συμπεριφοράς**.
- **Φάση 2 (μελλοντικά, σταδιακά):** το `TournamentManager` σπάει ανά οθόνη **μόνο όταν δουλεύουμε έτσι κι αλλιώς σε μια οθόνη**. Όχι μαζική διάσπαση.

### 1.4 Στάδιο 5A (μόνο για ενημέρωση — ΔΕΝ υλοποιείται στο R)

Το 5A γίνεται **ενιαίο στάδιο**, όχι 5A.1–5A.4. Ο λεπτομερής σχεδιασμός και το changelog του θα γίνουν στο chat μετά το R. Αποφάσεις μέχρι στιγμής:

- Σύνδεση διαχειριστή **μόνο με Google** (Firebase Authentication, popup). Το Email/Password παραμένει ενεργό στο Firebase για μελλοντική χρήση.
- **Ατομικοί λογαριασμοί:** κάθε διαχειριστής (ο Γιάννης και 1–2 συνεργάτες για έλεγχο και debugging) μπαίνει με το δικό του Google.
- **Λίστα διαχειριστών στη Firestore:** `users/{uid}` με `email` και `role: "admin"`. Υπάρχει **ένα μόνο επίπεδο** σήμερα, και όλοι οι διαχειριστές είναι ισότιμοι. Η λίστα δεν γράφεται στον κώδικα ούτε στους κανόνες.
- Κάθε διαχειριστής προστίθεται με **ρητή ενέργεια του Γιάννη**. Ο πρώτος (ο Γιάννης) προστίθεται από το Firebase console, με το UID που δείχνει η εφαρμογή στο μήνυμα «Δεν έχετε δικαιώματα».
- **Κεντρικός έλεγχος δικαιωμάτων:** μία συνάρτηση (π.χ. `can(action, target)`) που ρωτά όλη η εφαρμογή, ώστε αργότερα να επεκταθεί σε υπερ-διαχειριστή και διαχειριστές συλλόγων χωρίς αλλαγές σε κάθε κουμπί.
- Στο ίδιο στάδιο: τα **στοιχεία επικοινωνίας** μεταφέρονται σε ιδιωτική συλλογή, γράφονται **κανόνες Firestore** (δημόσια ανάγνωση, εγγραφή μόνο από διαχειριστές, `users` αλλάζει μόνο από το console) με αρχείο `firestore.rules` μέσα στο repo, και **καταργείται ο παλιός κοινός κωδικός**. Μένει ένα build, αλλά η εφαρμογή του στην παραγωγή γίνεται με σειρά βημάτων και επαληθεύσεις, ώστε κανείς να μην κλειδωθεί έξω.
- Μελλοντικά (όχι στο 5A): υπερ-διαχειριστής (ο Γιάννης) και διαχειριστές ανά σύλλογο. Ανοιχτό ζήτημα για τότε: ποιος δημιουργεί, διορθώνει ή ενώνει πρόσωπα στο κοινό μητρώο.
- Η υλοποίηση του 5A προτείνεται να γίνει στο Claude Code, λόγω της δοκιμής κανόνων στον Emulator.

## 4. Build R2 — Διάσπαση Φάση 1 (χωρίς αλλαγή συμπεριφοράς)

Έλεγξε ότι κανένα άλλο σημείο δεν αναθέτει σε μεταβλητή ενότητας.
5. Το component `TournamentManager` μένει στο `App.jsx` και δεν σπάει σε αυτό το build.
6. Το `firebase.js` δεν αλλάζει.

## 5. Build R3 — Νέο changelog

### 5.1 Μορφή `src/config/changelog.js`

```js
// Νεότερο πρώτο. Τρέχουσα ημέρα: μία καταχώρηση ανά build (με version).
// Προηγούμενες ημέρες: μία ημερήσια σύνοψη (χωρίς version).
// audience: "all" = όλοι, "admin" = μόνο διαχειριστές.
export const CHANGELOG = [
  { version: "2026-10-10.03", date: "2026-10-10", items: [
    { text: "…", audience: "all" },
  ]},
  { date: "2026-10-09", items: [
    { text: "…", audience: "all" },
    { text: "…", audience: "admin" },
  ]},
];
```

### 5.2 Συμπεριφορά

- **Σελίδα Σχετικά → Changelog:** ως τίτλος εμφανίζεται το `version` στις καταχωρήσεις build και η ημερομηνία στις ημερήσιες συνόψεις, π.χ. «9 Οκτωβρίου 2026». Ο επισκέπτης βλέπει μόνο γραμμές `"all"` και δεν βλέπει καταχωρήσεις που έμειναν κενές. Ο admin βλέπει όλες.
- **Ένδειξη «νέο»:** το κλειδί κάθε καταχώρησης είναι `version ?? date`. Μια καταχώρηση είναι αδιάβαστη όταν το κλειδί της είναι αλφαβητικά μεγαλύτερο από την τιμή του `WHATS_NEW_SEEN_KEY`. Παράδειγμα: το `"2026-10-09"` είναι μεγαλύτερο από το `"2026-10-08.20"` και μικρότερο από το `"2026-10-09.11"`, οπότε η σύγκριση δουλεύει και μετά τη σύμπτυξη. Η κουκκίδα εμφανίζεται μόνο αν υπάρχει αδιάβαστη γραμμή **ορατή στον τρέχοντα χρήστη**. Η αποθήκευση του «είδα» μένει όπως σήμερα (`APP_BUILD_VERSION`).
- Το `FEATURES_SUMMARY` αντικαθίσταται με το κείμενο του §5.4. Το `TECHNICAL_SUMMARY` δεν αλλάζει.
